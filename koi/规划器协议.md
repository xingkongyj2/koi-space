# 规划器协议与历史

实现入口：`app/python/koi_agent/planner.py`。规划器只负责目标理解、澄清与子目标计划，不控制浏览器。任务是否完成仍由执行器和验证器判断。

## 决策规则

1. 读取本会话完整历史，合并本轮补充，保留用户已确认的目标、网址和约束。最新明确更正覆盖旧信息。
2. 不需要网页且信息充分时返回 `direct`。
3. 需要网页时，先明确 HTTP(S) 入口。用户给出的 URL 优先；明确裸域名可补协议，唯一明确的公共站点可用其官方首页。未知深链从已知入口查找，不编造链接。
4. 网站有歧义或必要条件不足时返回 `ask`。之后每轮仍按完整历史判断，只追问尚缺信息，允许连续多轮确认。
5. 信息齐全后返回 `ready`，拆分 1～12 个有意义的子目标；纯导航只需一个。不能把“打开网站并搜索/提取”等复合任务当作仅打开网页。

## 固定输出

每种状态都必须返回同样的五个顶层字段；每步固定八个字段。不允许未知字段、缺失字段、字符串形式的布尔值或 `null`。

```json
{
  "status": "ready",
  "needs_browser": true,
  "question": "",
  "direct_answer": "",
  "steps": [
    {
      "id": "s1",
      "goal": "打开 https://example.com/",
      "success_criteria": ["url_prefix:https://example.com/"],
      "depends_on": [],
      "start_url": "https://example.com/",
      "needs_user_confirmation": false,
      "risk": "low",
      "parallel_group": ""
    }
  ]
}
```

| 状态 | needs_browser | question | direct_answer | steps |
|---|---|---|---|---|
| ready | true | 空字符串 | 空字符串 | 1～12 项 |
| ask | 按任务是否需要浏览器填写 | 必须非空 | 空字符串 | [] |
| direct | false | 空字符串 | 必须非空 | [] |

`depends_on` 表示**直接前置节点**，始终为数组，以便支持多个分支汇合。无依赖用 `[]`，不能用空字符串。

| 情形 | 依赖 |
|---|---|
| 单任务 | s1: [] |
| 两个独立任务 | s1: []；s2: [] |
| 串行 | s1: []；s2: ["s1"] |
| 两个独立分支汇合 | s1: []；s2: []；s3: ["s1", "s2"] |

步骤按拓扑顺序排列。未知节点、自依赖、重复依赖、向后引用、环都会被拒绝。`parallel_group` 只是辅助提示；同组不能有直接或间接依赖，调度依赖以 `depends_on` 为准。当前执行循环仍串行消费计划，本次没有引入多标签页并行调度。

每步必须有合法 `start_url` 与至少一个完成条件。当前支持 `url_prefix:<完整 URL>`、`url_contains:<非空片段>`、`text_contains:<非空文本>`；所有条件必须满足。这三类页面断言并不等同于任意数据提取或复杂任务的完整验收能力，后续扩展 Validator 时应同步扩展契约。

## 完整历史链路

`SessionDb.session_events → SessionManager.getSessionHistory() → runEngine → Python stdin.history → Planner.plan(history=...) → 模型输入`

- 初次启动和每次追问/恢复都传入当前会话所有事件，包含本轮用户消息，不截取最近 N 条，也不截断消息正文。应用重启后从 SQLite 恢复。
- 事件包括用户输入、通知/回复、完整有效计划、工具调用与结果、错误，以及子目标开始/完成/重试/等待确认/失败状态。
- Python 运行期间由 `protocol.capture_events` 继续追加事件，后续调用规划器时可复用同一份列表。网页全文和底层诊断日志不等于对话消息，不额外灌入历史。
- 运行进展与旧计划通过现有 `thinking` 事件持久化，内部 JSON 的 `kind` 为 `planner_plan` 或 `task_progress`；实际完成状态以验证器记录为准。
- `Planner.plan(user_input, history=..., context=...)` 的 `context` 可补充本次执行状态或重规划触发原因。当前主循环尚未接入自动 L3 重规划；恢复/后续输入会重新调用规划器。
- 增量计划只包含剩余子目标，已验证结果保留在历史中并可复用。历史已完成前置条件不再作为本次计划的节点依赖。
- 显式“重新运行”保留产品原有的新对话语义；“继续/追问/恢复”保留原会话历史。
- 全量历史超出模型上下文限制时应显式报错，不悄悄删除旧消息。

系统提示词通过 Responses API 的 `instructions` 发送，历史/当前输入/状态放在 `input` 中；静态规则和历史前缀保持稳定。参见 [OpenAI 官方文本生成说明](https://developers.openai.com/api/docs/guides/text)。

正常规划调用模型一次。解析失败时带着完整原始上下文、错误输出和具体校验错误纠正一次；仍失败则报告错误，不执行无效计划。网页、历史工具输出和被拒绝的模型输出都不应被当作系统规则。

未配置模型时，仅支持明确的“打开/访问 <完整网址>”导航；不能仅因复杂任务中含 URL 就生成伪成功计划。提示词命中效果仍需通过实际模型与代表性任务评估，单元测试验证的是契约和历史链路。
